# RK3588 硬件压缩（Web 界面使用说明）

本文只说明 **Web 前端（`src/webapp`）** 的使用方式，不涉及后端实现细节。
界面上的配置项与后端契约 `on_record_finished.rk3588` 一一对应：

```yaml
on_record_finished:
  burn_subtitles: false        # 保留原有烧录配置
  burn_delete_ass: false
  burn_delete_source: false
  rk3588:
    enable: false              # 硬件路径总开关（手动压缩也要求为开）
    compress: false            # 录制完成后压缩（无 ASS 也压缩；有 ASS 则烧录+压缩一次完成）
    codec: hevc_rkmpp          # hevc_rkmpp(H.265) / h264_rkmpp(H.264)
    bitrate: 4M                # 目标码率，默认 4M
    decode_fallback: true      # 硬解失败时回退软解
    scale_width: 0             # 0 表示不缩放
    scale_height: 0            # 0 表示不缩放
```

> 前端默认值定义在 `src/webapp/src/types/hardware.ts` 的 `RK3588_CONFIG_DEFAULTS`，
> 如需调整默认编码器或默认码率，改这一个常量即可。

### 三个开关的语义

| 开关 | 作用 |
| --- | --- |
| `enable`（启用 RK3588 硬件路径） | 硬件路径总开关：处理阶段使用 RK3588 MPP 硬件编解码；**手动压缩也要求该项为开** |
| `compress`（录制完成后压缩） | 录制结束即使没有 ASS 弹幕字幕也会压缩；**关闭时不会自动压缩**，仅手动压缩或烧录等处理会用到硬件路径 |
| `burn_subtitles`（烧录弹幕字幕） | 控制是否烧录；有 ASS 时**烧录与压缩一次完成** |

## 一、全局配置

路径：**设置 → GUI 模式 → 全局设置 → 「RK3588 硬件压缩」卡片**

卡片上半部分是「硬件压缩状态（探测 + 自检）」，下半部分是压缩参数：

| 字段 | 说明 | 默认 |
| --- | --- | --- |
| 启用 RK3588 硬件路径 | 硬件路径总开关：处理阶段使用 RK3588 MPP 硬件编解码，手动压缩也要求为开 | 关闭 |
| 录制完成后压缩 | 录制结束即使没有 ASS 弹幕字幕也压缩；有 ASS 时烧录与压缩一次完成 | 关闭 |
| 视频编码器 | H.265 / HEVC（`hevc_rkmpp`）或 H.264 / AVC（`h264_rkmpp`） | `hevc_rkmpp` |
| 码率 | 例如 `4M`、`4000k`、`4000000`；合法范围 10k~200M，留空按默认 4M 处理 | `4M` |
| 硬解失败回退软解 | 硬件解码失败时仅回退为软件解码 | 开启 |
| 输出宽度 | 单位像素，0 表示不缩放 | 0 |
| 输出高度 | 单位像素，0 表示不缩放 | 0 |

修改后点页面底部「保存设置」，保存的是完整全局配置（含 `on_record_finished.rk3588`）。

### 缩放填写注意

- 宽高都填 0：保持原分辨率；
- 宽高都填写：按填写的分辨率输出，尺寸需为 **16~8192 之间的偶数**（与后端校验一致）；
- 只填一个方向、填奇数或超出范围：保存时表单校验不通过，并给出中文原因（例如“缩放需宽高同时填写，或都填 0 保持原分辨率”）。

## 二、按房间继承与覆盖

路径：**设置 → 直播间设置 → 展开某个直播间 → 「RK3588 硬件压缩（覆盖全局）」**

- 「按房间覆盖压缩参数」**关闭**：该房间继承全局设置，界面上的字段为只读置灰状态，并在下方显示当前继承到的全局参数；
- **开启**：字段可编辑，保存时只提交本房间的 `on_record_finished.rk3588`；
- 原来已覆盖过的房间再关闭该开关并保存：前端提交 `on_record_finished.rk3588 = null`，表示清除本房间覆盖、恢复继承全局。

顶部还会显示「继承自全局」标签与全局参数摘要，便于确认当前生效来源。

> 房间级覆盖需要后端在房间配置更新接口中支持 `on_record_finished` 子字段合并。

## 三、文件列表压缩

路径：**文件列表**

- **单个文件**：视频文件行的操作列新增「压缩」按钮（与「重命名 / 上传 / 删除」并列）；
- **多个文件**：勾选文件后，工具栏出现「批量压缩 (N)」，N 为选中项中可压缩的视频数量。

点击后会弹出中文确认框，内容包含：

1. 将压缩的文件数量与文件名列表；
2. **当前压缩参数**（编码器 / 码率 / 缩放 / 硬解回退，来自当前生效配置）；
3. 若硬件路径未开启（`enable=false`），提示手动压缩要求先开启，并给出开启路径；
4. 若硬件状态为不可用（真实编解码自检未通过），提示任务可能失败并回退软解，并注明自检结果不等于所有真实录像都可用；
5. 删除与保留说明（按**当前生效设置**如实显示）：
   - 已开启「烧录后删除源视频」（`burn_delete_source=true`）→ 提示“成功完成全部处理阶段后可能删除源视频，任务失败时一定保留原件”；
   - 未开启 → 提示“成功后保留原文件并生成压缩文件，任务失败同样保留原件”；
   - 已开启「烧录后删除 ASS 文件」时，确认框会额外标注；
6. 提示提交后可在「队列」页面查看真实执行命令与日志。

确认后调用批量压缩接口，结果会提示「已入队 N 个压缩任务」，被跳过的文件会列出具体原因（路径越权、文件不存在、非视频文件、入队失败等）。

> 单文件压缩复用批量压缩接口，只是路径列表里只有一个元素。
>
> 手动压缩只要求 `enable` 为开，后端会忽略 `compress`：`compress` 仅控制“录制结束后即使没有 ASS 弹幕字幕也自动压缩”。

## 四、硬件状态说明（探测与自检 ≠ 所有录像都可用）

「硬件压缩状态（探测 + 自检）」卡片展示 `GET /api/hardware/status` 的内容：

| 项 | 说明 |
| --- | --- |
| 硬件可用状态 | 后端返回的 `available`，**以真实编解码自检结果为准** |
| 硬件路径已启用 / 未启用 | 后端返回的 `enabled` |
| 就绪 / 未就绪 | 后端返回的 `ready` |
| 真实编解码自检 | `self_test.ok` / `codec` / `message`，并区分「本次实测」与「缓存结果（`self_test.cached`）」 |
| 自检步骤 | `self_test.steps[]`：每步显示中文名（编码 / 解码 / 硬解）、通过或失败、耗时、实际命令行（可复制）与失败原因 |
| 自检时间 | `self_test.tested_at`（真正跑自检的时间，与状态生成时间不同） |
| 状态生成时间 | `probed_at`（本次状态响应的生成时间） |
| 实际配置编码器 | 当前生效配置中的 `codec`，并标注是否出现在探测列表中 |
| 实际配置参数 | 码率、缩放、硬解回退、录制完成后压缩开关（后端返回） |
| FFmpeg | `ffmpeg_version` 与 `ffmpeg_path` |
| 硬件加速方式 | `hwaccels` |
| 处理链路 | `chain` |
| 探测到的硬件编码器 / 硬件解码器 | `encoders` / `decoders` |
| 处理链所需滤镜（探测到） | `filters` |
| 设备节点 | `devices` 中每个设备节点是否存在 |
| 后端告警 | `warnings` |
| 重新探测并自检 | 带 `?refresh=1` 请求，强制后端重新自检（忽略后端缓存） |

界面明确标注：

- 编码器、解码器、滤镜与硬件加速列表都是 **FFmpeg 探测结果**，只表示当前环境“报告支持”；
- `available` **以后端真实编解码自检为准**；自检通过也只代表本次自检样本可用，**不等于所有真实录像、所有码率与分辨率都能成功**；
- 实际执行结果以 **队列页任务里的执行命令与日志** 为准；
- 若实际配置的编码器未出现在探测列表中，或自检未通过（卡片显示“硬件自检未通过”橙色告警），说明实际执行时可能失败或回退，失败时保留原文件；
- 前端对状态请求有 15 秒缓存，点「重新探测并自检」会带 `?refresh=1` 强制后端重测（后端自检另有 10 分钟缓存，`refresh=1` 会真正重跑编码/解码/硬解步骤）；
- 自检步骤里的命令行可点击复制：复制走 antd 的实现，优先 Clipboard API，在 HTTP 等不安全上下文会自动降级为 `document.execCommand('copy')`。

## 五、硬解失败与回退口径

「硬解失败回退软解」开启时的准确含义（界面同文案）：

> 硬件解码失败时**仅回退为软件解码（软解）**，不会自动切换到其他硬件编码器，也不保证任务一定成功；失败时保留原文件。

## 六、队列页与失败保留原件

路径：**队列**（`/tasks`）

- 展开任务可看到每个阶段的**真实执行命令**（可复制）与**执行日志**；
- 压缩与烧录在同一个阶段内完成，阶段名显示为「烧录字幕」；
- 状态为失败（fail）的任务**保留原始文件**，不会删除原件；
- 成功时是否删除源视频取决于「烧录后删除源视频」（`burn_delete_source`）：开启时会在全部处理阶段完成后删除源文件；
- 页面顶部新增说明：手动入队的压缩/烧录任务会出现在这里，压缩与烧录同阶段完成，失败保留原件，探测与自检结果不等于所有真实录像都可用。

## 七、前端调用的接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/hardware/status` | 硬件（FFmpeg/MPP）探测 + 真实编解码自检状态，`?refresh=1` 强制重测 |
| POST | `/api/pipeline/batch-compress` | 批量压缩，请求体 `{ paths: string[] }`，返回 `{ enqueued, skipped, task_ids }` |
| GET | `/api/config/effective` | 读取当前生效配置（用于确认框展示压缩参数） |
| GET | `/api/lives/{id}` | 读取房间自身覆盖配置（`room_config.on_record_finished`） |

接口不可用时的降级行为：

- `/api/hardware/status` 不可用：状态卡片提示「未能获取硬件状态」，压缩参数仍可配置，不会阻塞压缩入口；
- `/api/config/effective` 读取失败：确认框显示「未读取到配置（按后端默认执行）」。

## 八、已知边界

1. **依赖后端支持**：若后端尚未实现 `on_record_finished.rk3588`，保存不会报错，但不会生效（刷新后回到默认值）；状态卡片在拿不到硬件状态时也会给出该提示。
2. **房间级覆盖按子字段合并**：只提交 `rk3588` 不会影响该房间已有的 `burn_*` 覆盖；提交 `rk3588: null` 表示清除本房间覆盖、恢复继承全局。
3. 手动压缩只要求 `enable` 为开，后端忽略 `compress`；`compress` 只影响“录制结束后无 ASS 也自动压缩”。
4. 压缩与烧录同属一个阶段，所以队列页中手动压缩任务的阶段名也是「烧录字幕」。
5. 码率与缩放按后端同口径在前端先校验（码率 10k~200M；缩放 16~8192 的偶数或都为 0），实际是否被编码器接受仍由后端/FFmpeg 决定。
6. **原文件保留不是无条件的**：失败一定保留原件；成功后是否删除源文件由 `burn_delete_source` 决定，界面与确认框都按当前设置显示，不宣称“成功后也永远保留”。
7. 压缩入口只对视频文件（`.mp4/.flv/.ts/.mkv/.avi/.mov/.wmv/.webm`）开放。

## 九、复制降级的实测记录（HTTP 环境）

用户规则要求页面在 http 下复制必须能降级，本次实测结论（真实浏览器 + 非安全上下文）：

- 测试地址：`http://192.168.10.62:8098/#/tasks`（内网 IP，`window.isSecureContext === false`，`navigator.clipboard` 为 `undefined`）；
- 用真实鼠标手势点击队列页「执行命令」的复制按钮后：走的是 `document.execCommand('copy')` 降级路径且返回成功，`copy` 事件里取到的文本与任务执行命令完全一致，页面无未捕获错误（8/8 项断言通过）；
- 因此队列页、自检步骤里的复制按钮在 http 下可正常使用；
- 另外，**直播列表页**原有两处直接调用 `navigator.clipboard.writeText(...)` 的复制按钮在 http 下会直接抛错（`navigator.clipboard` 不存在），现已统一改为 `src/webapp/src/utils/common.ts` 的 `copyTextToClipboard()`：优先 Clipboard API，失败或不可用时降级 `document.execCommand('copy')`。

局部验证命令见下一节；复制助手另有单测（`src/webapp/src/utils/common.test.ts`）覆盖 http 降级、Clipboard 被拒绝、两条路径都失败三种情况。
